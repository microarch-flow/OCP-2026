# Bridging Compute and Memory Fabric: Data Services for Direct XPU Access

## 核心结论
“GPU direct I/O”只改变谁发起/搬运，并不自动消除细粒度读取放大。对低算术强度、依赖式随机访问，更值得比较的是 **拉原始数据** 与 **发送查询并返回结果**。[[fti-workshop-data-centric-computing/Bridging-Compute-and-Memory-Fabric-Data-Services-for-Direct-XPU-Access.pdf#page=7|PDF p.7]] [[fti-workshop-data-centric-computing/Bridging-Compute-and-Memory-Fabric-Data-Services-for-Direct-XPU-Access.pdf#page=8|PDF p.8]] [[fti-workshop-data-centric-computing/Bridging-Compute-and-Memory-Fabric-Data-Services-for-Direct-XPU-Access.pdf#page=9|PDF p.9]]

## 关键证据
CPU-driven 路径同时承担控制和数据；CPU-assisted XPU direct 去掉 staging，但控制并发和同步仍可能受 CPU 限制；XPU-driven 把 I/O stack 移入加速器，仍要承担 polling、access control、线程同步和介质粒度放大。[[fti-workshop-data-centric-computing/Bridging-Compute-and-Memory-Fabric-Data-Services-for-Direct-XPU-Access.pdf#page=5|PDF p.5]] [[fti-workshop-data-centric-computing/Bridging-Compute-and-Memory-Fabric-Data-Services-for-Direct-XPU-Access.pdf#page=6|PDF p.6]] [[fti-workshop-data-centric-computing/Bridging-Compute-and-Memory-Fabric-Data-Services-for-Direct-XPU-Access.pdf#page=7|PDF p.7]]
HNSW 的小节点、依赖式遍历难以提前知道后继地址；幻灯片的“prefetching is not an option”应理解为该访问模式的挑战，不是所有 HNSW 预取技术均不可能。[[fti-workshop-data-centric-computing/Bridging-Compute-and-Memory-Fabric-Data-Services-for-Direct-XPU-Access.pdf#page=8|PDF p.8]]

## 指标与条件
|例子|输入条件|原页结论与核对|
|---|---|---|
|Vector search|1M vectors、96D FP32（384 B）、ef=100、batch=16K、topK=10、约 600 comparisons|约 3.8 GB 原始读 vs 64 MB 结果、约 60× 数据量缩减；属示例记账而非端到端 60× speedup。[[fti-workshop-data-centric-computing/Bridging-Compute-and-Memory-Fabric-Data-Services-for-Direct-XPU-Access.pdf#page=9\|PDF p.9]]|
|Embedding gather+sum|batch=2K、8 tables、每表10 lookups、128D FP32|约 84 MB→8.4 MB，10× 数据量减少；未测完整模型吞吐。[[fti-workshop-data-centric-computing/Bridging-Compute-and-Memory-Fabric-Data-Services-for-Direct-XPU-Access.pdf#page=11\|PDF p.11]]|

p.9 有两处应显式保留的瑕疵：图下方写“768D”，右侧 scenario 写“96D”；3.8 GB 计算式漏写 batch 因子。按 96D、16,384 queries 计算，600×384×16,384≈3.77 GB，结果 16,384×10×(384+4)≈63.6 MB，才匹配 headline。本笔记不把矛盾隐藏为确定 benchmark。

## 图表与架构
服务模型把容量层/性能层、promotion/demotion、安全、变换与统一访问接口放进 data tier；CPU 编排、XPU 执行模型、数据处理器执行检索/聚合。[[fti-workshop-data-centric-computing/Bridging-Compute-and-Memory-Fabric-Data-Services-for-Direct-XPU-Access.pdf#page=12|PDF p.12]] 控制路径和加速数据路径分离，不等于每次请求都零 CPU。

## 关联与比较
[[knowledge/concepts/compute-memory-ndp-contract|近数据卸载契约]]：需要声明输出大小、所需访问权限、函数语义和结果完成。[[knowledge/concepts/compute-memory-capacity-vs-datapath|收益归因]]：数据缩减比不能直接乘为推理 tok/s 倍数。

## 不确定性与待验证
示例不含 queueing、网络竞争、结果质量/recall、服务启动开销、近端 compute 上限。应补查同容量同算法的延迟/吞吐及端到端 critical path；本文不引用其他演讲或外链替本例补实验条件。
