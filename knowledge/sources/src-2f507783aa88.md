# Arm：Agentic CPU 应同时度量单任务进度和满足 SLA 的机架吞吐

## 核心结论
Agentic 系统不能只用 token/s 或单核跑分评价 CPU。编译/测试型任务需要单任务进度，企业短工具调用需要并发吞吐；更合适的机架指标是 **tasks/s @ SLA**，同时保留单 agent 延迟。[[executive-sessions/45_Rethinking CPU Performance for the Agentic AI Era presented by Arm.pdf#page=4|PDF p.4]][[executive-sessions/45_Rethinking CPU Performance for the Agentic AI Era presented by Arm.pdf#page=8|PDF p.8]]

## 关键证据
- 提出观察真实 agent 运行→对轨迹聚类选代表样本→冻结状态、工具、时间与检查条件→重放同一 CPU 工作负载，减少模型路径变化对硬件比较的干扰。[[executive-sessions/45_Rethinking CPU Performance for the Agentic AI Era presented by Arm.pdf#page=7|PDF p.7]]
- 并发上升后，CPU、内存、存储竞争会破坏响应；p.9 为没有数值坐标的概念曲线，不能读取“最大并发”。[[executive-sessions/45_Rethinking CPU Performance for the Agentic AI Era presented by Arm.pdf#page=8|PDF p.8]][[executive-sessions/45_Rethinking CPU Performance for the Agentic AI Era presented by Arm.pdf#page=9|PDF p.9]]
- 厂商引用 Signal65 机架级结果，相对 AMD EPYC Turin：Terminal-Bench 1.93×、SWE-bench 2.00×、MySQL 1.43×、NGINX 1.95×、Milvus 1.54×、vLLM 1.88×、fastText 3.19×。这些不是同一个端到端 agent 成功率。[[executive-sessions/45_Rethinking CPU Performance for the Agentic AI Era presented by Arm.pdf#page=11|PDF p.11]]

## 指标与条件
p.11 未在正文完整展开服务器数量、功率预算、内存、软件配置与 SLA，完整方法另有外链，本文未独立复核。p.10 的 200–400 W 和最多2×机架密度是设计范围/厂商主张，不应解释为同配置每核快2×。[[executive-sessions/45_Rethinking CPU Performance for the Agentic AI Era presented by Arm.pdf#page=10|PDF p.10]][[executive-sessions/45_Rethinking CPU Performance for the Agentic AI Era presented by Arm.pdf#page=11|PDF p.11]]

## 图表与架构
p.7 的冻结轨迹有可复现性价值，但会固定工具选择与失败重试，不能替代真实 agent 全链路质量与动态反馈评估；应同时运行可重放组件测试和端到端在线测试。[[executive-sessions/45_Rethinking CPU Performance for the Agentic AI Era presented by Arm.pdf#page=7|PDF p.7]]

## 关联与比较
与 OpenAI 的用户体验约束下能量/token 思路相接：CPU orchestration、KV、工具响应都属于服务关键路径，GPU 吞吐优势不等于任务完成率优势。

## 不确定性与待验证
需相同任务集合、成功判据、尾时延、并发、整机/机架功率与成本；不能仅据这份厂商引用结果宣称某 CPU 全面胜出。
