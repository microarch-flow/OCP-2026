# Bridging On-Prem and Cloud — GPU Networking at Meta Scale

## 核心结论
云GPU采购应购买**可复现的collective/workload行为与遥测权限**，而不仅是GPU型号与端口线速。Meta将性能保证写进合同，并把问题从handoff后前移到供应商验收。[[networking/Bridging On-prem and Cloud - GPU Networking at Meta Scale.pdf#page=6|PDF p.6]][[networking/Bridging On-prem and Cloud - GPU Networking at Meta Scale.pdf#page=8|PDF p.8]][[networking/Bridging On-prem and Cloud - GPU Networking at Meta Scale.pdf#page=12|PDF p.12]]

## 关键证据
- CSP在topology、load balancing、CC、lossless/lossy transport上异构；统一软件接口不等于相同网络行为。[[networking/Bridging On-prem and Cloud - GPU Networking at Meta Scale.pdf#page=4|PDF p.4]][[networking/Bridging On-prem and Cloud - GPU Networking at Meta Scale.pdf#page=5|PDF p.5]]
- 验收含ib_write_bw/lat、IPv6多跳、NCCL/RCCL Alltoall/Allreduce/Allgather/ReduceScatter，从16到512+ GPUs及长时稳定性。[[networking/Bridging On-prem and Cloud - GPU Networking at Meta Scale.pdf#page=8|PDF p.8]]
- 推理示例：remote KV cache经CPU写到RDMA NIC，slow receiver触发PFC向上游扩散；建议CC与通信库限速。后训练trainer→sampler权重传输是incast，需另调PFC buffer；预训练并发ring需调load balancing。[[networking/Bridging On-prem and Cloud - GPU Networking at Meta Scale.pdf#page=10|PDF p.10]]
- 有host baremetal权限但switch telemetry必须逐CSP约定metric set、格式、频率；pinger只补黑盒覆盖，不能替代交换机证据。[[networking/Bridging On-prem and Cloud - GPU Networking at Meta Scale.pdf#page=12|PDF p.12]]

## 指标与条件
- 32条parallel rings、每ring 16 GPUs，NCCL bus BW对message size：调flowlet timer+CC后峰值58.4→75.5 **GB/s**，约+29%，跨run波动收窄。是工作负载吞吐测试，**没有p99/ITL量化**。[[networking/Bridging On-prem and Cloud - GPU Networking at Meta Scale.pdf#page=11|PDF p.11]]
- 作者称目前从签约到production onboarding比首个CSP快5倍；未给绝对时长、同规模匹配条件，属流程案例而非通用采购周期。[[networking/Bridging On-prem and Cloud - GPU Networking at Meta Scale.pdf#page=13|PDF p.13]]

## 图表与架构
已核p.7/10/11/13。p.7某CSP由custom CC/无PFC/aggressive retrans变为无CC/PFC/两lossless class/relaxed retrans，是为Meta特定历史栈实现on-prem parity的个案，**不是推荐所有推理关闭CC**。p.10对slow receiver反而明确要求调CC。

## 不确定性与待验证
没有透露CSP身份、完整拓扑和具体flowlet/CC参数。采购应补TP/EP/KV分离流量、small message、p50/p99/ITL、failure recovery、遥测保存与排障责任，而不是照搬训练ring的峰值提升。
