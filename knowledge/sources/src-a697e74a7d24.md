# Managing Orchestration Memory with the CMS Memory Fabric Manager

## 核心结论
把fabric memory接到Kubernetes不是一个“增加RAM”的动作；需要同时选择 **谁拥有内存（kernel或application）** 和 **何时/在哪个scope分配（node或running pod）**。这决定了调度、权限、生命周期与resize控制路径。

## 关键证据
- System-RAM是CPU-less NUMA node，由kernel page allocator管理、可用malloc/mmap和NUMA/tiering；devdax是`/dev/daxX.Y`应用直接管理region，支持精确region暴露，但需要DAX-aware代码且不自动tiering。p.4对cross-host sharing的适配描述不等于自动提供cache coherence。[[Server：Composable Memory Systems/Managing Orchestration Memory with the CMS Memory Fabric Manager.pdf#page=4|PDF p.4]]
- DRA负责global discovery/capacity/device/host selection和scheduler integration；NRI负责local DAX/device binding/runtime injection/online-offline/container config。[[Server：Composable Memory Systems/Managing Orchestration Memory with the CMS Memory Fabric Manager.pdf#page=5|PDF p.5]]
- 四象限：node System-RAM扩容；pod System-RAM在线resize；node固定devdax；pod动态devdax units。四者底层均由MFM in-band agent执行host memory操作。[[Server：Composable Memory Systems/Managing Orchestration Memory with the CMS Memory Fabric Manager.pdf#page=6|PDF p.6]]
- 关键不对称：System-RAM每次resize走NRI UpdatePodSandbox；devdax在CreateContainer预置device-cgroup权限与mount propagation，之后agent按pressure增减extent，无新的NRI往返。原因是讲者设计所针对runtime没有为running container重新应用CDI spec的等价机制。[[Server：Composable Memory Systems/Managing Orchestration Memory with the CMS Memory Fabric Manager.pdf#page=7|PDF p.7]] [[Server：Composable Memory Systems/Managing Orchestration Memory with the CMS Memory Fabric Manager.pdf#page=11|PDF p.11]]

## 指标与条件
无性能benchmark或resize latency测量。p.9的8→32→8GiB是agent工具负载**示例**。材料引用Kubernetes KEP1287/v1.35 GA等版本状态，本文仅保留演讲时点设计依据，不对当前Kubernetes实现做外部核验。[[Server：Composable Memory Systems/Managing Orchestration Memory with the CMS Memory Fabric Manager.pdf#page=9|PDF p.9]]

## 图表与架构
p.3已核对MFM pod包含core、monitor、Auth/Log、Security/RAS、GUI/CLI；worker含in-band agent、DRA/NRI plugin与perf exporter；control node含DRA controller，out-of-band agent连switch/device管理面。p.11 ResourceSlice更新是**事后accounting而非调度gate**，因pod已在运行。[[Server：Composable Memory Systems/Managing Orchestration Memory with the CMS Memory Fabric Manager.pdf#page=3|PDF p.3]] [[Server：Composable Memory Systems/Managing Orchestration Memory with the CMS Memory Fabric Manager.pdf#page=11|PDF p.11]]

## 关联与比较
[[knowledge/concepts/compute-memory-kv-placement|KV placement]] 的placement决策只有可安全执行的allocation/release路径才有意义；[[knowledge/concepts/compute-memory-cxl-failure-domain|故障域与可观测性]] 需要管理面与运行时共同实现隔离回收。

## 不确定性与待验证
Workstream软件requirements仍in progress，白皮书rev1.1及Pangaea是贡献方向。[[Server：Composable Memory Systems/Managing Orchestration Memory with the CMS Memory Fabric Manager.pdf#page=2|PDF p.2]] 应验证capacity撤回时live KV的迁移/失效、内存清零、tenant权限、压力回路振荡与数据面反压；材料没有证明动态管理是“免费”或不会影响p99。
