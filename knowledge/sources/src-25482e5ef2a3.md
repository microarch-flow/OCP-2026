# Last Inch Synchronization: How to Get Time to the Software Level

## 来源身份与核心结论
文件路径为Timing Recovery Using PTP…，实际首页标题如上。NIC PHC精确不意味着CPU/GPU软件时间精确；last inch要比较software read、PCIe PTM与物理ePPS，且须计route delay/PLL/buffer/level shift。[[Time Appliances/Timing Recovery Using PTP within NIC and Distribution by ePPS to Computing Modules.pdf#page=1|PDF p.1]][[Time Appliances/Timing Recovery Using PTP within NIC and Distribution by ePPS to Computing Modules.pdf#page=3|PDF p.3]][[Time Appliances/Timing Recovery Using PTP within NIC and Distribution by ePPS to Computing Modules.pdf#page=11|PDF p.11]]

## 关键证据
PTM是双向带timestamp的PCIe协议；ePPS把10MHz tick与top-of-second用duty cycle编码，ToD仍经软件。Flex IO定义TX/RX freq/sync接口，二者接口边界不同。[[Time Appliances/Timing Recovery Using PTP within NIC and Distribution by ePPS to Computing Modules.pdf#page=6|PDF p.6]][[Time Appliances/Timing Recovery Using PTP within NIC and Distribution by ePPS to Computing Modules.pdf#page=7|PDF p.7]]

## 指标与条件
- ITU-T活动中的last-inch等级例：普通PCIe±2µs、PTM±200ns、physical PPS/ePPS±50ns，是文件描述的标准化目标，不是所有设备测得精度。[[Time Appliances/Timing Recovery Using PTP within NIC and Distribution by ePPS to Computing Modules.pdf#page=5|PDF p.5]]
- 两级PTM引用Calnex setup，理想PTP输入，CPU压力导致图中offset变动；不能与单级轻负载PTM15ns峰峰值不分条件地相减。[[Time Appliances/Timing Recovery Using PTP within NIC and Distribution by ePPS to Computing Modules.pdf#page=8|PDF p.8]]
- ePPS理想源下NIC1PPS mean -1.89ns、min-3.8/max-0.05、p-p3.75ns；host recovered mean -2.55ns、min-4.3/max-0.08，表写p-p3.5ns。[[Time Appliances/Timing Recovery Using PTP within NIC and Distribution by ePPS to Computing Modules.pdf#page=10|PDF p.10]]

## 图表与架构
已核p.8/10。**p.10 host min/max与p-p存在算术不一致**：按列应为4.22ns而表为3.5ns；本卡保留原值并不代作者修正。PTM表约50ns用RMS合成口径，不能与ePPS peak-to-peak直接比倍率。

## 不确定性与待验证
源为理想无噪声，现实主要误差可能来自PTP network PDV/asymmetry/servo。需真实network load、PCIe hops、thermal/route compensation与仪器trace后定预算；没有业务吞吐或p99改善实测。
